## Current architecture

- **Frontend:** React 18 + TypeScript + Vite SPA; shadcn/ui (Radix + Tailwind); TanStack Query for server state; React Router with four routes (`/`, `/auth`, `/dashboard`, `/reset-password`). Route guarding is a client-side redirect for UX only — **RLS is the real security boundary**.
- **Backend:** Supabase — Postgres 17, Auth (JWT, localStorage-persisted sessions), Storage, PostgREST, and three **deployed** Edge Functions: `fetch-paper-metadata` (PubMed/Crossref metadata, v14), `analyze-paper` (Google Gemini analysis, v15), and `get-gemini-provider-quota` (v3). The third is **deployed but intentionally unused** — its manager-facing dashboard is **deferred under C29** (Gemini Free Tier during development; automatic provider-quota monitoring paused until commercialization), so **no frontend calls or renders it**; it remains as deferred infrastructure. A fourth function, **`delete-account` (PFA-C04), exists in the repository and is NOT deployed to Production** — its Production deployment is a separately authorized mutation that must happen *before* the frontend merge, so the Danger-zone button never points at a missing endpoint (see [deployment.md §7a](deployment.md)). All four authenticate the caller with the caller's JWT via in-body `auth.getUser()` (`verify_jwt = false` at the gateway is intentional; CORS `*` is an accepted decision under bearer-token auth). The first three use **no** elevated key; `delete-account` additionally builds a **server-only** elevated client (the Edge runtime's auto-provided `SUPABASE_SECRET_KEYS`, falling back to `SUPABASE_SERVICE_ROLE_KEY`) because Auth administration and Storage cleanup require it — that key is never sent to the browser, never returned, and never logged, and **no `VITE_*` variable carries any secret key**.
- **Read path:** all filtering, sorting, pagination, keyword matching, and full-text search happen in Postgres; the client holds one page at a time. Detail: [architecture-read-path.md](architecture-read-path.md).
- **Search:** four mutually exclusive modes (empty / short ILIKE for 1–2 chars / prefix-aware FTS for 3+ chars / quoted literal phrase), across six fields (title, abstract, authors, journal, notes, keywords) with a server-driven "Matched in:" attribution line.
- **Security patterns (mandatory for new code):**
  - **S1:** every `SECURITY DEFINER` RPC verifies caller identity against `auth.uid()` (explicit guard or internally derived ownership). Full inventory and rule: [decisions-and-triggers.md](decisions-and-triggers.md) §Security decisions.
  - **S2:** client-side mutations/reads on `user_id`-bearing tables carry an explicit `.eq("user_id", userId)` predicate as defense-in-depth, with nullable-safe `userId` threading.
- **Attachments:** private Storage bucket, owner-scoped path policies, size/MIME limits, server-side storage-quota triggers.

## Implemented capabilities

- Papers CRUD, bulk actions (select-all across the full filtered set), and column/layout customization.
- Import by PMID/DOI identifiers — including structurally authenticated PubMed record URLs and DOI resolver URLs — and from BibTeX / RIS / PubMed NBIB / EndNote tagged / CSV files, with atomic server-side bulk insert. Structured sources (the PubMed API, native NBIB) state publication types as discrete values, and those boundaries are persisted in the nullable `papers.raw_publication_types` — the application never reconstructs them by splitting the legacy joined `raw_study_type`, which stays as the human-readable/fallback representation.
- Duplicate detection — **PMID/DOI-only by decision**. The duplicate-merge RPC exists and its **successful merge path is repaired and live in Production**: `MERGE-EXACT-DUPLICATES-JSONB-REPAIR-001` was merged through PR #184 and deployed as migration `20260807141402_repair_merge_exact_duplicates_jsonb`. Successful merge behavior is covered by the dedicated `005_merge_exact_duplicates_success.test.sql` database regression suite.
- Projects, tags, and four curation pools: keywords, synonyms, study types, exclusions.
- Per-paper notes (indexed into search) and saved searches / filter presets (server-side per user, RLS-isolated).
- Exports to CSV / RIS / BibTeX of the current selection/filter (chunked pipeline for large libraries), plus a separate **full account export** — **Settings → Account data** downloads one versioned ZIP (`paperlume-account-export`, format version 1) covering the signed-in user's whole dataset regardless of filters: papers (with notes), projects, tags, both relationship tables, filter presets, all four pools, attachment metadata **and** attachment binaries, and a whitelisted non-secret profile. Client composition over existing SELECT-own reads and private Storage reads only — no migration, RPC, or Edge Function. Secrets are excluded by construction (`profiles.pubmed_api_key` is never selected; no Session/User object is serialized), and the export is complete-or-fail: any unreadable category or missing attachment binary aborts the run rather than downloading a partial archive.
- Per-paper file attachments in the private Storage bucket, within the server-enforced storage quota. **Settings → Storage** renders a read-only used/quota/remaining gauge for the signed-in user (transparency only — no upgrade, checkout, or purchase path; the database trigger stays the enforcement boundary).
- AI analysis (TL;DR, study type, statistical methods) via Gemini, behind the server-enforced AI quota.
- Per-user optional PubMed API key (stored in `profiles`, used server-side by `fetch-paper-metadata`).
- **Self-service account deletion** — **Settings → Danger zone** permanently deletes the signed-in account after the user types `DELETE MY ACCOUNT` exactly. It is a **hard** deletion, not a soft delete, deletion request, or grace period: the privileged `delete-account` Edge Function derives the target **solely from the authenticated bearer token** (the client sends no user id at all), removes every Storage object under the account's `{userId}/` prefix through the Storage API **before** touching Auth, then calls `auth.admin.deleteUser(userId, false)`; the user's database rows go with it through the pre-existing `ON DELETE CASCADE` foreign keys. PFA-C02's full account export is the **export-before-delete** path and is offered next to it. Function code is present but **not yet deployed to Production**.

PFA-C04-SELF-SERVICE-ACCOUNT-DELETION-001 — **Settings → Danger zone now permanently deletes the signed-in Paperlume account.** The destructive action opens its own dialog and stays disabled until the user types `DELETE MY ACCOUNT` exactly; the phrase is re-checked **server-side**, so the client gate is ergonomics, not security. The client posts `{ confirmation }` to the new privileged `delete-account` Edge Function and **sends no user id at all** — the function answers the CORS preflight first, accepts only `POST`, requires a bearer header, validates that exact token with an authoritative `auth.getUser(token)` call, and derives the target **only** from the authenticated user, so a `user_id` in the body or query string cannot redirect the deletion and there is no owner/manager exemption. Order is load-bearing: the caller's `{userId}/` Storage namespace is enumerated **from Storage itself** — recursive, paginated, depth-bounded, so an orphaned binary whose `paper_attachments` row is gone is still removed — deleted in batches of at most 1,000 paths (the documented Storage limit), and only then is the Auth user **hard**-deleted via `auth.admin.deleteUser(userId, false)`. Supabase refuses to delete a user who still owns Storage objects, so a Storage failure aborts with the account intact rather than reporting success; cross-service atomicity is impossible, so the operation is instead **safe to retry** and a post-Storage Auth failure is reported honestly as retryable. On success the browser clears its own session, drops every cached query, and hard-navigates to `/auth`. **No migration, no deletion RPC, no schema/RLS/grant/Storage-policy change, and no new npm dependency** — owned rows already cascade from `auth.users`, now pinned by the new `008_account_deletion_cascade` pgTAP suite (79 assertions), which also proves no `public` FK to `auth.users` can block a hard delete and that `storage.objects` does **not** cascade (hence the Storage step). `subscriptions.user_id` / `subscription_events.user_id` remain **deliberately** `ON DELETE SET NULL`: those rows survive unlinked, and that retention must be re-evaluated against legal/privacy requirements before commercial launch. A destructive Playwright spec deletes a **disposable per-run local account** through the real UI and the real local function — never the deterministic fixtures, never Production. **The function is not deployed to Production; that deployment is separately authorized and must precede the merge.** No billing/paywall/upgrade path was added (C27 unchanged).

4. DOI-RESOLVER-LINK-ENCODING-001 — **DOI resolver links are built by canonical percent-encoding rather than raw interpolation, and the change is live in Production.** PR #198 is merged (`ca2f0542c7fcd8c7ec43f8425ac2f188a15c2d56`) and `fetch-paper-metadata` is deployed as **v14** with `verify_jwt = false` preserved. Several output paths built the link as `` `https://doi.org/${doi}` ``, so URL-significant characters that are legal DOI-name data turned into URL *syntax*: `10.1000/456#789` produced a link whose `#789` a browser reads as a fragment, and the paper never resolves — it must be `https://doi.org/10.1000/456%23789`. A DOI **name** and its resolver **URL** are two different representations, and the conversion between them is now explicit: prefix and suffix are encoded separately and rejoined with the single structural `/`, so a suffix-internal `/` becomes `%2F` while the prefix/suffix separator stays literal; a literal `%` becomes `%25` and an apparent `%xx` is never assumed to be already encoded; `#`, `?`, comma, spaces, quotes and Unicode are encoded per UTF-8 byte. The builder deliberately does **not** trim or otherwise normalize DOI-name code points — a trailing space is real data, so `10.1000/example ` becomes `…/example%20`. The representation boundary holds in both directions: **identifier** fields still carry raw DOI names (CSV `DOI`, RIS `DO`, BibTeX `doi`), only **resolver-URL** fields are encoded (CSV URL / RIS `UR` / BibTeX `url` exports, plus the PubMed, Crossref, and `fetchByDoi` metadata paths), and **provider-API encoding stays separate** (`api.crossref.org/works/<encodeURIComponent(doi)>`, PubMed `<encodeURIComponent(doi)>[doi]`). **No migration and no historical backfill** — `journal_url` is a generic external-link field that may legitimately hold a publisher URL rather than a resolver link, so stored values were left untouched and change only when normal activity re-fetches metadata. **No schema, RPC, RLS, dependency, lockfile, or CI-workflow change.**

IMPORT-DOI-URL-DETECTION-001 — **DOI resolver URLs now enter the DOI metadata path, and the change is live in Production.** PR #196 is merged (`b9d65337d8393de1956ebd145521adbeaa25a690`) and that rollout deployed `fetch-paper-metadata` as **v13** with `verify_jwt = false` preserved; the detection behaviour remains present in the current **v14**. `10.1000/example` and `doi:10.1000/example` already took the DOI path, but `https://doi.org/10.1000/example` — the form the DOI Foundation and Crossref both document as canonical, and the one a reader copies out of a reference list — was classified as a *title* and sent to free-text search. Recognition and the handoff both had to change. Recognition is **structural, never substring-based**: the WHATWG `URL` parser decides from `protocol` + `hostname` + `pathname` only, http(s) with the hostname compared exactly against `doi.org` and the still-resolving `dx.doi.org`, so a near-host, a suffix-host, the `…@evil.example` user-info form, a foreign URL carrying a DOI URL in its query or fragment, and a scheme-less `doi.org/10.1000/example` all **fail closed** to the existing title path, with no scheme ever guessed. The handoff matters just as much: `detectIdentifier()` now returns `{ type: "doi"; doi }` and the provider dispatch consumes that authenticated value, since a raw resolver URL reaching a provider that expects a DOI *name* would fail however it was labelled. The DOI is read from the path only, kept whole (suffix slashes included), and percent-decoded exactly once so the provider layer’s own encoding cannot double-escape it. **Bare PMID, PubMed record URLs, bare and `doi:` DOIs, title fallback, provider precedence, structured publication types, and bulk ordering/accounting are unchanged. No schema, migration, RPC, RLS, dependency, or lockfile change.**
