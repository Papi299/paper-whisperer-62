## 2. Current architecture

- **Frontend:** React 18 + TypeScript + Vite SPA; shadcn/ui (Radix + Tailwind); TanStack Query for server state; React Router with six routes (`/`, `/auth`, `/dashboard`, `/extension-import`, `/reset-password`, `/privacy`). Route guarding is a client-side redirect for UX only — **RLS is the real security boundary** — and `/privacy` deliberately carries no guard at all: it is the one public, unauthenticated route.
- **Backend:** Supabase — Postgres 17, Auth (JWT, localStorage-persisted sessions), Storage, PostgREST, and Edge Functions (see §5 — all six deployed).
- **Read path:** all filtering, sorting, pagination, keyword matching, and full-text search happen in Postgres; the client holds one page at a time. Detail: [architecture-read-path.md](architecture-read-path.md).
- **Search:** four mutually exclusive modes (empty / short ILIKE for 1–2 chars / prefix-aware FTS for 3+ chars / quoted literal phrase), across six fields (title, abstract, authors, journal, notes, keywords) with a server-driven "Matched in:" attribution line.
- **Attachments:** private Storage bucket, owner-scoped path policies, size/MIME limits, server-side storage-quota triggers, and a **durable, recoverable cleanup lifecycle** (see §2a).
- **Chrome extension:** a second build target in the same repository and dependency graph (`extension/`, its own Vite config → `dist-extension/`, no second `package.json`). On a toolbar click it classifies the active tab's URL as a PubMed record or a DOI and — **only** where the URL identifies neither, on an ordinary http(s) page — reads four standard bibliographic `<meta>` keys (`citation_doi`, `dc.identifier`, `dc.identifier.doi`, `prism.doi`) out of that one tab's `document.head`, because a DOI resolver redirects to the publisher before a user can reach the toolbar. For a recognised paper it offers **Continue in PaperLume**, which opens **one new tab** at the Production `/extension-import` handoff (below) through `chrome.tabs.create`. It requests `activeTab` and `scripting`, and nothing else: **no declared host permissions**, no `tabs`, no `storage`, no content script, no background context. Invoking the toolbar action is what makes `activeTab` grant temporary host access to that one current tab, and that grant is what permits both reading its `Tab.url` and injecting into it — `scripting` enables the API but reaches no page on its own, which is what makes the pair narrower than a host permission; a real Chromium confirms `chrome.permissions.getAll()` → `origins: []` and refuses a real `executeScript` with no toolbar grant. A PubMed record or a `doi.org` link is still answered from the address with the page never touched, and a page publishing two conflicting DOIs fails closed rather than picking one. It makes **no network or API request of its own** (the DOI is never resolved against doi.org or Crossref), holds **no** PaperLume or Supabase session, persists nothing, sends no page content or source URL, and **cannot import**: the new tab's page owns authentication, Projects/Tags, duplicate handling and the explicit confirmation that writes. Its entire privileged surface is `chrome.tabs.query`, `chrome.tabs.create` and `chrome.scripting.executeScript`, pinned by a source-boundary test and re-checked on the built artefact by the package contract. It ships the production PaperLume icon set at 16/32/48/128 in both `icons` and `action.default_icon`; those PNGs are **not** committed under `extension/` — the extension's Vite config copies them out of the canonical brand pack (`assets/brand/png/`) at build time, byte for byte, so the packaged icon cannot drift from the mark. It packages to a deterministic Store-ready ZIP (`npm run package:extension`, gitignored `release/`) and is exercised in a real Chromium against the **built** output (`npm run test:extension:browser`), where Chrome itself reports the granted permissions as `["activeTab","scripting"]` with zero host origins. Loaded unpacked; **not** published to the Chrome Web Store. As of 2026-08-30 a **draft** Store item exists (`cfanjbamcemoeglgkpbidnclkomaocmo`, package `0.1.0` uploaded) whose **Store Listing, Privacy, Test instructions and Distribution pages are populated and saved** — Category `Workflow & Planning`, Language `English (United States)`, visibility `Unlisted`, regions `All regions` — and it is **NOT submitted and NOT published**. Readiness, policy risk and the remaining gates are in [chrome-web-store-readiness.md](chrome-web-store-readiness.md).
- **Extension import handoff:** `/extension-import?kind=pmid|doi&value=…` is an authenticated route that receives one identifier — from the extension above or from anyone else, with no sender treated as privileged — and nothing else; no token, no session material, no user id, no taxonomy id, no metadata. The value is validated against the application's existing PMID/DOI grammar with no title fallback, opening the route **mutates nothing**, and the import runs through the same `bulkImportPapers` the Add Papers dialog uses, with the same `NormalizationConfig`, only after an explicit confirmation. **A duplicate is now resolved rather than only reported (CHROME-EXTENSION-IMPORT-001D, C36 — migration `20260903180000` verified live in Production as of 2026-09-11, and its database/RPC semantics accepted there the same day):** `safe_bulk_insert_papers` returns the existing paper's id when — and only when — exactly one row owned by the caller matches the attempted PMID or DOI under the same semantics `idx_papers_user_pmid_unique` and `idx_papers_user_doi_unique` enforce, and this route then **adds** the selected Projects/Tags to that row through `bulk_add_paper_projects` / `bulk_add_paper_tags`, never the replace-all `bulk_set_*`, so everything the paper was already filed under survives. Two identifiers naming two different owned rows, and any collision with no provable row, return no id and perform no assignment — the route says the selection was not applied rather than choosing a candidate. Acting on the id is an explicit per-call opt-in (`applyAssignmentsToResolvedDuplicates`), and this route is its only caller: Add Papers, PubMed Search and file import keep skipping duplicates untouched. The absent-id answer is also exactly what a database predating that migration returns, which is why the web half could safely ship before the database half ([deployment.md](deployment.md) §6.3).

### Attachment lifecycle — durable and recoverable

An attachment lives in two systems that cannot share a transaction: its metadata row in Postgres and its binary in the private `attachments` Storage bucket. The lifecycle is built around that fact.

- **Storage.** Private bucket, keys shaped `{userId}/{paperId}/{uniqueName}`, four owner-scoped `storage.objects` policies keyed on the first path segment, 20 MB object limit, fixed MIME allow-list, signed URLs only. Unique names are generated per upload and never reused.
- **Metadata and quota.** `paper_attachments` holds the row; `user_storage_usage.used_bytes` is maintained by a BEFORE INSERT consume trigger and an AFTER DELETE refund trigger (`20260521030000`). Quota tracks **metadata**, so a binary awaiting cleanup is already refunded while still physically present. That is deliberate; changing it is a separate Product decision.
- **Cleanup queue** (`20260904120000`, ATTACHMENT-ORPHAN-CLEANUP-HARDENING-001). `public.attachment_cleanup_queue` is a durable, owner-scoped record of Storage keys whose metadata is already gone. RLS enabled and forced; `authenticated` holds SELECT-own and DELETE-own and **no INSERT or UPDATE** — a queue row is a deletion instruction, so only the server may create one. Rows cascade with `auth.users`.
- **Atomic enqueue-before-delete.** `delete_attachment_with_cleanup(uuid)` and `delete_papers_with_attachment_cleanup(uuid[])` record the cleanup intent in the **same transaction** that removes the metadata making the object reachable, so a path can never stop being reachable without the database still knowing it.
- **Serialized upload finalization.** `finalize_attachment_upload(uuid, text, text, text, integer)` is the **only** writer of attachment metadata on this schema. It takes a transaction-scoped advisory lock on `(auth.uid(), file_path)` before reading anything, then returns `metadata_committed`, `metadata_present` (an earlier attempt already committed — nothing is queued) or `cleanup_queued` (the metadata INSERT was rejected; the row and the quota it consumed roll back in a subtransaction while the cleanup intent commits). Repeating the call is safe, which is what makes a lost HTTP response survivable: the browser asks again instead of guessing, and can no longer delete a valid attachment's binary. It requires `READ COMMITTED` and refuses to run otherwise.
- **Serialized against paper deletion.** `finalize_attachment_upload` and `delete_papers_with_attachment_cleanup` take the same per-paper advisory lock — deletion before it snapshots the attachment paths it will queue, finalization before its first read — so a paper cascade can never destroy an attachment whose path the snapshot missed. Locks are taken path-then-paper, and deletion takes its paper locks in sorted order, which is what makes the protocol deadlock-free.
- **The tombstone.** `public.attachment_cleanup_tombstone` records that an uploaded path was finalized as garbage and is kept **after** the cleanup queue row for it has been acknowledged and deleted. Without it, a duplicated finalization arriving after the drain would find no metadata and no queue row and create metadata for a binary that is already gone. No client role holds any privilege on it and it has no policy of any kind; it cascades with the account. `trg_paper_attachments_block_cleanup_intent` refuses any `paper_attachments` INSERT whose `(user_id, file_path)` has a pending intent **or** a tombstone — including a direct client INSERT — so metadata and cleanup intent for one path are mutually exclusive as a property of the table, not of one function's callers.
- **The lifecycle boundary, on both tables.** Since `20260904120000`, `authenticated` holds **`SELECT` only** on `paper_attachments` — `INSERT`, `UPDATE`, `DELETE` and `TRUNCATE` are revoked, from `anon` too, and nothing is granted to `PUBLIC`. The parent has the same treatment for the same reason: `paper_attachments.paper_id` cascades from `papers`, so a direct paper deletion removes attachment metadata without any statement naming it, and `DELETE`/`TRUNCATE` on `papers` are revoked as well (`SELECT`/`INSERT`/`UPDATE` are untouched — creating and editing papers is not this feature's business). Attachment metadata is created and destroyed exclusively by the three lifecycle RPCs, the cascade they initiate, and account deletion. That is what makes *"Postgres never removes attachment metadata without recording the Storage cleanup intent in the same transaction"* an invariant of the database rather than a convention of the current React bundle — a hand-written Data API request gets `42501` before RLS is consulted. The database half is **two migrations with a mandatory operator checkpoint between them** — `20260904110000` retires the legacy child-first `merge_exact_duplicates`, the checkpoint proves every invocation of the old body has drained, and only then may `20260904120000` run (it refuses otherwise); see [deployment.md](deployment.md) §6.4. The cutover takes `SHARE ROW EXCLUSIVE` on `auth.users`, then `SHARE` on `papers`, then `ACCESS EXCLUSIVE` on `paper_attachments` as its first three locking statements and holds all three to commit, because a `REVOKE` locks catalog rows and not the table: without the barrier a metadata `INSERT` or a paper `DELETE` authorized before the cutover could still commit after it, and the Storage fence would then be evaluated against a row that had not committed yet. Every mode and the order itself are derived. Parent-before-child, and `SHARE` rather than something stronger, is the only ordering that cannot deadlock against an in-flight attachment write — whose foreign-key check needs `ROW SHARE` on `papers` — so `delete_papers_with_attachment_cleanup` and `merge_exact_duplicates` each take their `papers` lock before touching `paper_attachments` to stay on the right side of it. And `auth.users` comes before both, because the queue and tombstone tables reference it and adding a foreign key takes `SHARE ROW EXCLUSIVE` on the referenced table: taking that lock last — which is what an implicit foreign-key acquisition does — deadlocks against an ordinary account deletion holding `auth.users` and cascading downstream into exactly the two tables the migration would already be holding.
- **The Storage fence.** `attachments_owner_delete` now also requires that no live `paper_attachments` row names the object. The owner-prefix boundary is unchanged; this is an added condition. It is what stops a browser tab still running the pre-migration bundle from executing either historical destructive ordering — deleting the binary of a metadata row whose write actually committed, or deleting a binary before its metadata row. Account deletion is unaffected: it sweeps Storage with the elevated role, which bypasses RLS.
- **Bounded, stable drain.** The browser drains its own queue by repeatedly reading the **head** and advancing by deleting what it finishes — never by offset, because a second tab draining the same queue would shift rows out from under an offset walk and make this one skip them.
- All three client RPCs are `SECURITY DEFINER`, derive the caller from `auth.uid()`, pin `search_path=public`, and are executable by `authenticated` only.
- **Retry, bounded.** Physical removal is done by the authenticated browser through the existing Storage owner-DELETE policy — no Edge Function, no service-role key, no scheduler. It is attempted immediately after the user's action and once more when an authenticated session starts (`useAttachmentCleanupRecovery`, mounted once in the Dashboard shell). There is no timer, no polling and no cron.
- **Final sweep.** If the user never returns, the queue row waits. Account deletion remains the last resort and still enumerates **Storage itself** — recursively and paginated, never from `paper_attachments` or the queue — so it also catches orphans that predate this feature and orphans no queue row ever described.

Documentation must not claim every binary is deleted immediately, or that cleanup is guaranteed for a user who never comes back. Neither is true without a server-side worker, and this design deliberately does not add one.

### Security invariants — mandatory for new code

- **S1:** every `SECURITY DEFINER` RPC verifies caller identity against `auth.uid()` (explicit guard or internally derived ownership), including an explicit `auth.uid() IS NULL` rejection. Full inventory and rule: [decisions-and-triggers.md](decisions-and-triggers.md) §Security decisions.
- **S2:** client-side mutations/reads on `user_id`-bearing tables carry an explicit `.eq("user_id", userId)` predicate as defense-in-depth, with nullable-safe `userId` threading.
- **No secret key ever reaches the client.** No `VITE_*` variable carries an elevated key. The one Edge Function that needs elevated privileges (`delete-account`) builds a server-only client and never returns or logs that key.
- Least-privilege `EXECUTE` across the SECURITY DEFINER surface (no `PUBLIC`/`anon`/`service_role`), both-owner relational RLS, and bounded `search_path` on all functions are live in Production and pinned by the database suites (§7).
- **Data API relation and sequence privileges are stated, never inherited.** A migration that creates a table, view or sequence in `public` must `REVOKE` by role and then `GRANT` its exact intended surface — that is **D2**, and the default-privilege hardening does not relax it. **D1a** is a second layer, not a substitute: for objects `postgres` creates in `public`, the live TABLE and SEQUENCE defaults now give `PUBLIC`, `anon` and `authenticated` **no** privilege, so a forgotten ACL fails closed instead of shipping an exposed relation, while `service_role`'s default is deliberately preserved rather than narrowed. D1a does not replace D2: it cannot reach an object another owner creates, and it cannot touch functions. `PUBLIC` and `anon` are intended to hold **nothing** on any `public` relation or sequence (function EXECUTE is a separate, unaddressed question), `authenticated` exactly the per-table matrix, and `service_role` is out of scope by decision. RLS does **not** govern `TRUNCATE`, `TRIGGER` or `MAINTAIN`, which is why those are revoked rather than left to policy. Pinned catalog-driven by `supabase/tests/database/015_data_api_acl_matrix.test.sql`, and **live in Production since 2026-09-11** (C38, `20260910212202`).

## 3. Implemented capabilities

- Papers CRUD, bulk actions (select-all across the full filtered set), and column/layout customization.
- Import by PMID/DOI identifiers — including structurally authenticated PubMed record URLs and DOI resolver URLs — and from BibTeX / RIS / PubMed NBIB / EndNote tagged / CSV files, with atomic server-side bulk insert. Structured sources state publication types as discrete values, persisted in the nullable `papers.raw_publication_types`; the application never reconstructs them by splitting the legacy joined `raw_study_type`, which stays as the human-readable/fallback representation. The same principle covers authorship: what a source stated about each mention (personal vs collective, name components, affiliations, identifiers, ORCID) is persisted in the nullable `papers.author_provenance`, index-aligned with `authors`, and is never derived by parsing an author string.
- **In-app PubMed discovery (PUBMED-IN-APP-SEARCH-001) — live in Production.** Add Papers has a fourth mode, **PubMed Search**: a query goes to the read-only `search-pubmed` Edge Function (ESearch → ESummary), results are paged 20 at a time, and the user multi-selects records and imports them. The load-bearing boundary is that **discovery finds PMIDs and the existing importer imports them**: the selected PMID strings go into the exact `onBulkImport` callback the Import IDs tab uses, so there is no second normalization, no second insert payload and no second duplicate check, and no ESummary field is ever persisted. Search is explicit (never on keystroke), the query reaches PubMed unrewritten, a stale response cannot repopulate a newer or reset session, the four modes share **one** `selectedProjectIds`/`selectedTagIds` intent, and the whole discovery session is ephemeral — nothing is persisted to storage, URL or profile. A result's publication-type badges are filtered through the current user's existing Study Type Exclusion Pool by trim-aware, case-insensitive, whole-value matching (never substring, so `Clinical Trial` does not hide `Clinical Trial, Phase II`); that is **display-only** and changes neither what is imported nor the study type the importer records. The endpoint-before-UI deployment rule for any future contract change is in [deployment.md](deployment.md) §7b.
- Duplicate detection — **PMID/DOI-only by decision**. The duplicate-merge RPC's successful merge path is live in Production and covered by a dedicated database regression suite.
- Projects, tags, and four curation pools: keywords, synonyms, study types, exclusions.
- Per-paper notes (indexed into search) and saved searches / filter presets (server-side per user, RLS-isolated).
- Exports to CSV / RIS / BibTeX of the current selection/filter (chunked pipeline for large libraries), plus a separate **full account export** — **Account menu → Account → Account data** downloads one versioned ZIP (`paperlume-account-export`, format version 2) covering the signed-in user's whole dataset regardless of filters, including attachment binaries, a whitelisted non-secret profile projection, and the saved AI-model preference. Client composition over existing SELECT-own reads and private Storage reads only. Secrets are excluded by construction (`profiles.pubmed_api_key` is never selected; no Session/User object is serialized), and the export is complete-or-fail.
- Per-paper file attachments in the private Storage bucket, within the server-enforced storage quota. **Settings → Storage** renders a read-only used/quota/remaining gauge (transparency only — no upgrade or checkout path; the database trigger stays the enforcement boundary).
- AI analysis (TL;DR, study type, statistical methods) via Gemini, behind the server-enforced AI quota, with a header usage indicator and an actionable message when the server returns the AI `402`.
- **AI organization suggestions (AI-PROJECT-TAG-SUGGESTIONS-001) — live in Production and Production-accepted.** Both halves are live: the `001A` backend contract and the `001B` Edit Paper experience, which is **frontend-only** against that pre-existing endpoint contract. The `suggest-paper-organization` Edge Function compares one owned paper against the caller's own Projects and Tags and returns four suggestion lists (existing Projects, existing Tags, proposed new Projects, proposed new Tags), each with a short reason. It is **advisory**: it creates nothing, assigns nothing and persists nothing, and its only writes are the existing `consume_ai_quota` / `refund_ai_quota` RPCs — one AI request per successful generation, refunded when the provider fails or returns an unusable result. **No database identifier reaches Gemini**: Projects/Tags cross the boundary as request-local `P1`/`T1` refs whose map lives for one request, and an existing-entity suggestion resolves **only** through that map — no name-based fallback, no fuzzy matching — so an invented ref resolves to nothing. Name comparison is used for one separate purpose only: deciding whether a proposal the model labelled *new* already exists. That promotion happens only when the comparison identifies exactly one row; an ambiguous match (possible because the application key trims and the database key does not) is dropped rather than resolved to a guess. A library past the supported bound fails honestly rather than being silently truncated, and a title-only paper is refused before a unit is spent. **The endpoint is deployed and ACTIVE, and the `001A` backend contract was verified against Production on 2026-08-23** — refusal paths (preflight, method, auth, malformed, title-only, foreign paper) all behaved correctly and cost no quota, and one real generation returned the four suggestion arrays for exactly one `ai_analysis` unit with no application-domain row changed. **`001B` Edit Paper Production acceptance completed separately on 2026-08-24**: a real generation returned suggestions with reasons, and both persistence paths were manually verified end to end against Production — selecting a suggested *existing* Project/Tag and pressing Save Changes, and **Create & select** on a proposed *new* one followed by Save Changes; in each case the assignment was still present after reopening the paper. Generation itself persisted nothing. **`001B` added the caller**: a compact **AI organization** section in Edit Paper, above the Projects selector, invoked only by an explicit click — never on open, on typing, on Save or on opening a selector — and disabled when the draft could not produce a useful answer. The request is built from the **unsaved** draft (title, abstract, parsed keywords, study type) plus the current local selection ids, because the user is asking about what they are editing, not about the stored row. **Accepting an existing Project/Tag changes local dialog state only** and persists through the ordinary Save Changes path, so cancelling assigns nothing; **a proposed new entity needs its own "Create & select" click**, which creates it immediately through the existing `createProject` / `createTag` mutations while the paper assignment still waits for Save — stated in the UI rather than implied. The client re-checks identity at action time: an existing suggestion is actionable only while its id is still in the taxonomy, and a proposed-new name is reconciled against the *current* taxonomy under the same `trim + lower` comparison, selecting a single match instead of duplicating it and refusing to guess when several match. Stale responses cannot land: a result commits only if the generation is still the newest, for the same paper, and for the same semantic draft — and once results are on screen, editing the draft marks them stale rather than letting old reasons describe new text. `001B` changed **no** Edge source and required no deployment, because the contract it calls is the one `001A` deployed and verified. Both actions spend the one `ai_analysis` counter, which is why the visible allowance is now named **"AI requests"** (display copy only — no RPC, column or hook was renamed). Decision C32 holds the durable architecture.
- Per-user optional PubMed API key (stored in `profiles`, used server-side by `fetch-paper-metadata`).
- Actionable first-run onboarding for an empty library, keyed off the **unfiltered** count so a filtered zero-result view is a distinct state. No persistent onboarding flag.
- **Author identity resolution is user-scoped and explicit** (AUTHOR-IDENTITY-RESOLUTION-001C — **live in Production**; see §5). Three deliberately separate layers: 001A compares author *strings* (`authorMentionKey`), 001B records what a *source* stated (`papers.author_provenance`), and 001C records what *this user decided*. Only the third creates a person, and only from an explicit action — there is no backfill, no import-time resolution and no background linker, so two historical papers sharing a valid ORCID stay two authors until someone links them. Identities never cross users: all five relationships are composite on `(user_id, …)` — alias → identity, link → identity, link → **paper**, and both merge endpoints — so a cross-user edge cannot be *stored*, not merely cannot be reached. A merge is a reversible edge (`source → target`), never a reassignment, so undo is one row deleted rather than a state reconstruction. Links are bound to `paper_id + author_index + author text`; a trigger clears a paper's links in the same transaction as any real change to its `authors` array, and the read layer independently refuses any link whose snapshot no longer matches. **Suggestions are advice, not authorization:** candidates come only from an exact valid ORCID or an exact 001A key and a contradicting ORCID suppresses the weaker name match, but the user can always search their own people and link or merge by hand — the contradiction is shown, both values stated, neither called wrong, and a two-step confirmation required. Because preferred names are deliberately not unique, every surface that names a person annotates it with that person's own evidence (ORCIDs, aliases, linked spellings, counts, a paper title), falling back to creation order when two are genuinely indistinguishable — never a UUID. There is no fuzzy, affiliation, coauthor or AI matching anywhere. A person's evidence is read account-wide, never from the current Analytics filter, so filtering changes what is *examined* and never what exists. Analytics counts one entity per resolved identity and one per unresolved 001A mention, and selections reconcile across link/merge/unmerge on read (`lib/authorSelection`) — internal entity keys are never displayed. **A failed identity read fails closed**: the hook distinguishes "not installed here" from "could not be read", so a real failure never masquerades as the benign 001A fallback — it is stated, nothing can be written against a graph nobody could read, and a last-known graph is kept on screen only while labelled as such.

- Internal `owner`/`manager` roles decoupled from the commercial plan (`internal_user_access` + read-only `get_current_user_access`), with an owner AI-quota exemption. Runtime authorization is **UUID/role-based, never email-based**.
- **AI model selection is live in Production end to end — foundation, server-side routing and the Settings control (AI-MODEL-SELECTION-001A + 001B + 001C, C33/C34).** The database foundation is applied to Production: a server-controlled `user_entitlements.ai_model_selection_enabled` capability flag, the `ai_model_catalog` allowlist (**live in Production with all four approved models** — Gemini 3.5 Flash, Gemini 3.6 Flash, Gemini 3.7 Flash and Gemini 3.8 Flash, in `sort_order` 10/20/30/40; 3.7 and 3.8 were added by migration `20260903120000`, **applied to Production on 2026-09-03**, C35), a one-row-per-user `user_ai_preferences` table, a fail-closed `can_select_ai_model` on `get_current_user_access` (mirrored as `useCurrentUserAccess().canSelectAiModel`), and two `auth.uid()`-derived RPCs — `set_current_user_ai_model` / `clear_current_user_ai_model` — that are the only write path. **001B is the deployed runtime:** `analyze-paper` and `suggest-paper-organization` share one resolver, `_shared/aiModelSelection.ts`, which re-checks `can_select_ai_model` on **every** AI operation and routes the Gemini call to a valid saved preference. Not entitled, no preference, dormant preference after a downgrade, a retired model (`enabled = false`), an unsupported provider, or **any** failure to read that metadata all fall back to the system-default `GEMINI_MODEL` — fail-closed on the paid capability, without turning into a quota error, a refund or a failed request. `enabled = true, selectable = false` still honours an already-saved choice; requiring both is the setter's job. Only the model component of the provider URL changes: prompts, bodies, parsing, quota, refunds and the 90s/0-retry transport are untouched, both models share the one existing `GEMINI_API_KEY`, and `get-gemini-provider-quota` stays system-default observational monitoring. **001C is the deployed Settings control** (merged as PR #268, merge commit `0ad72f6f4bb2a8cbb40ad1f7290f77b8c004de39`, and live in Production through the normal Vercel path): an **AI Model** section gated on `access.canSelectAiModel` alone — no plan name, email, role or browser-storage substitute — offering **Paperlume default** (a UI sentinel meaning *no saved row*, which calls the clear RPC and is never sent to the setter) plus the `enabled AND selectable` catalog rows from supported providers. Preference reads are `user_id`-scoped singletons and **every** write goes through the two RPCs; no frontend `INSERT`/`UPDATE`/`UPSERT`/`DELETE` touches either table, and opening Settings creates no row. Nothing is optimistic — the saved preference is refetched, only `saved = true` counts as success, and saving does not close the dialog. ### Responsive, mobile, and touch state

- The Dashboard has responsive smartphone controls: below `md` the navigation rail becomes a `Sheet` drawer, and the permanent mobile toolbar is compacted (Header + Search + Filters/More) so the paper table holds the majority of the viewport; secondary controls live in mobile overlays. Desktop composition is unchanged.
- Mobile searchable multi-selects render a shared touch-safe sheet: the heading is focused on open, the search field is **never** autofocused, and the option list is a plain scroll container sized from `window.visualViewport` so a software keyboard cannot bury it.
- **Coarse-pointer behavior is decoupled from the `<768px` layout breakpoint.** `(pointer: coarse)` describes how the user touches the screen; `useIsMobile()` (768px) describes how wide the screen is. A tablet legitimately gets the desktop composition *and* touch-safe focus. The 768px contract is unchanged and `useIsMobile()` remains its only JS reader.
- Reported tablet issues are addressed in the accepted implementation: Analytics is reachable at coarse-pointer tablet sizes (the controls region is an explicit bounded scroll owner) and touch hit targets meet size minimums.
- **Touch-safe initial focus is verified per surface, not claimed product-wide.** The surfaces owner testing has covered now decline Radix's text-field autofocus on a coarse pointer and focus their heading (or their popover panel) instead: the sidebar management dialogs, Save/Rename saved search, the Filters and Add Papers selectors, Analytics' Target Keywords/Authors selectors, Settings, Edit Project, Edit Tag, Add/Edit Synonym Group, Edit Paper, Edit Paper's Projects/Tags selectors, and the author identity manager. Tapping a field still focuses it, and a fine pointer keeps its existing autofocus everywhere. Surfaces outside that list have not been audited.
- Edit Paper bounds its shell to the **dynamic** viewport and gives its long form one deliberate scroll region (`overflow-y-auto` with `overscroll-contain` and `touch-pan-y`), so every section from Title to Save Changes is reachable by panning inside the dialog rather than by scrolling the page behind it. A `vh`-bounded shell is not reliable here, because `vh` resolves against the large viewport while browser chrome is on screen.
- Close-focus restoration is handled centrally in all three modal primitives — `DialogContent`, `SheetContent`, and `AlertDialogContent` — by capturing the opener on `onOpenAutoFocus` and restoring it on `onCloseAutoFocus`, because Radix otherwise restores through a trigger ref that is `null` for a controlled surface and drops focus on `<body>`. A consumer's own handlers still compose, and a consumer that calls `preventDefault()` wins. Confirmations that *do* have an `AlertDialogTrigger` (the exclusion-pool Clear controls) still restore their trigger correctly: the shared layer captures that trigger as the opener, and Radix's own trigger restore remains the fallback when no connected opener was captured. Where the opener is unmounted by the act of opening — the saved-search Delete/Update confirmations, launched from a dropdown item that closes with the menu — the call site names the persistent Presets trigger as its deliberate fallback; there is no global focus manager and no heuristic "nearest focusable" search.
- **Confirming a paper deletion is a handoff, not a restoration**, because the optimistic cache update unmounts the row and the Delete button that opened the confirmation. `PaperList` captures the deleted paper's neighbours by id *before* dispatching the delete, then moves focus to the **next** row's Delete button, falling back to the **previous** row when the last visible row was deleted, to whatever now occupies the same slot if both neighbours also vanished, and to the empty-state heading (`tabIndex={-1}`, never a Tab stop) when no row survives. Targets come from the `papers` array and refs registered per paper id — never a DOM search — and the handoff only claims focus that has nowhere to be, so a user who moved on during the asynchronous delete keeps their place. Dismissal is unchanged: Cancel and Escape never arm it.
- **Real-device iPhone/iPad verification remains a valuable validation source.** Chromium matching `(pointer: coarse)` proves which element receives focus and the geometry of hit targets; it cannot prove physical iOS software-keyboard or touch-pan behavior.
- This is responsive **web** usability only. **C7 still defers native/mobile packaging**, and none of it is a formal whole-product WCAG conformance audit.

## 7. Testing and CI model

- **There are two required merge gates: `validate` and `db-tests`.** `main` protection requires both — strict/up-to-date, administrators included, **zero** required human approvals, unresolved conversations block the merge, force-push and branch deletion disabled, regular merge commits allowed, Vercel **not** a required check, no repository rulesets.
  - **`Validate / validate`** — `.github/workflows/validate.yml` runs `npm ci`, lint, `npm run typecheck`, Vitest, the web production build and the **Chrome extension production build** on Node 22 for every pull request to `main` and every push to `main`. Both build targets are covered by the one required check, so neither can become an application CI does not execute.
  - **`DB Tests / db-tests`** — became required on **2026-08-16** when the owner resolved decision **D5** to `REQUIRE_DB_TESTS`. A red `db-tests` blocks merge; that is intended, not a reason to roll the gate back.
- **`E2E (local) / e2e-local` and `Extension / extension` run on eligible PRs but are NOT required checks.** All four workflows run on same-repository pull requests, skip fork-origin PRs before any execution, use `contents: read` only, and need **no** GitHub secret, variable, or Environment. `Validate`, `DB Tests` and `Extension` additionally run on every push to `main`; **`e2e-local` does not** — CI-E2E-EXECUTION-POLICY-001 removed its post-merge `push` trigger, because it re-ran the identical already-green candidate for another ~19 minutes, and replaced it with a **daily 02:17 UTC schedule** (`cron: '17 2 * * *'`) that GitHub runs from the latest commit on the default branch. That scheduled lane is a drift/health check, not a gate; the pre-merge PR run is unchanged. `Extension` is additionally **path-scoped on pull requests only**: a PR triggers it on the extension, its build config, its packaging, its browser lane, the lockfile — and on the shared web modules it bundles (`src/lib/pubmedIdentifiers.ts`, `src/lib/doiIdentifiers.ts`, `src/lib/extensionImportHandoff.ts`), because a change there is an extension change even though no file under `extension/` moved. Unrelated application PRs therefore do not pay for a browser download. Its `main`-push trigger carries **no** path filter, so every push to `main` runs it. `e2e-local` was deliberately **not** promoted under D5; reconsider it only against the recorded trigger — [decisions-and-triggers.md](decisions-and-triggers.md).
- **Required contexts are bare job names.** Branch protection matches the emitted check name — `validate` and `db-tests`, each bound to the GitHub Actions app — **not** the `Workflow / job` labels shown in the GitHub UI. Use the bare names in any protection change.
- **Fork-origin PRs would produce a vacuous green** on the required `db-tests` gate: the same-repository job condition makes it skip and report success. Harmless under today's same-repository-only model, but it must be resolved before fork contributions are accepted.
- **Local-first Playwright is the supported safe lifecycle.** `npm run test:e2e:local` starts an **ephemeral local Supabase stack**, replays every tracked migration, applies a deterministic local-only seed, and runs the suite behind a **two-layer fail-closed** Production/remote guard (Layer 2 runs in the browser before any credential read or fill). Raw key-bearing stack-startup output is suppressed.

It needs no live PubMed/Crossref, no served Edge Function and no provider credential, and it deletes the papers it imports.

It asserts at the metadata boundary that the selected PMIDs — and nothing else — reach the canonical importer, so a future change that inserts search summaries directly fails it. It needs no live NCBI egress and deletes every paper it imports.

Title, author, year, journal, abstract, URL and metadata similarity never participate, and no provider is consulted.
  - **Exactly one distinct owned candidate is the only sufficient proof.** Zero candidates and two-or-more candidates both fail closed: the row stays a duplicate, no id is returned, and no assignment happens. Do not propose a tie-break (constraint order, id order, recency, closest title) and do not propose asking the user to choose between candidates — that is a separate Product decision.
